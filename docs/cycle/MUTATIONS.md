# 突變追蹤紀錄

> `mutator` 提案的完整生命週期：**後設分析 → 具體提案 → 裁決 → 觀察介入後的影響**。
> 目前的黑板/KB機制只涵蓋到「裁決」——沒有人固定回頭看「這個提案被採納之後，
> 團隊/系統真的變好了嗎」。這份清單就是補這一段。

## 為什麼分開記（不是全部塞進 mutator 的 kb）

- `kb/mutator.md`：mutator 自己的判斷力（哪類提案值得認真提）。
- 這份 `MUTATIONS.md`：**跨代理人共用的追蹤表**——`wp-manager` 定期回頭填「觀察到的影響」
  這一欄，這是它「討論」的具體落地方式：不是跟 mutator 即時對話（`MAX_DEPTH=1` 不允許），
  是**非同步**地在同一張表上留下反應，讓下一輪 mutator（或主線）讀得到。

## 格式

| # | 日期 | 用的框架 | 後設分析（這個框架看出什麼問題，不是解法本身） | 具體提案 | 裁決結果 | wp-manager 的討論回應 | 觀察窗口後的影響（至少間隔一輪其他實質工作後才填） |
|---|---|---|---|---|---|---|---|

（目前尚無任何一筆——`mutator` 還沒被真的排過第一輪任務，見團隊健檢紀錄）

## 使用方式

1. **mutator 提案時**：新增一列，「後設分析」欄要能獨立成立——即使裁決者不同意具體提案，
   也該看得懂「用這個框架看，這裡確實有一個值得問的問題」。後設分析跟具體提案分開寫，
   避免「框架只是包裝、其實一開始就想好答案」。
2. **裁決者（`cycle-designer`／楊老師）處理完提案後**：回填「裁決結果」欄。
3. **`wp-manager` 每輪健檢**（見它自己 prompt 的「突變討論與追蹤」一節）：
   - 對**還沒被自己討論過**的提案：寫一段實質回應到「wp-manager 的討論回應」欄——
     不是「已轉交裁決者」這種轉發式的話，是真的讀完後設分析與提案，給出「這個角度我同意/
     不同意什麼、還缺什麼」的具體意見。這欄有內容之後，下次呼叫 mutator 時可以把它當輸入，
     讓 mutator 回應（形成非同步的來回，不是即時對話）。
   - 對**已裁決、且已經過至少一輪其他實質工作**的提案：回填「觀察到的影響」——用客觀證據
     （git log、黑板事件、下一輪相關產物），不要憑印象；還太早看不出影響就寫「觀察窗口未到，
     暫不填」，不要為了有東西寫而編。
4. **影響是負面或中性時，不要淡化**——如果一個被採納的突變提案事後看起來沒有實質幫助、
   甚至讓事情變複雜，如實記下來。這本身是「這類框架/這種提案在本專案有沒有用」的重要資料，
   之後 `mutator` 的 KB 該累積這個教訓。
