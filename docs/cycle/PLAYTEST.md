# 遊戲化玩法快速迭代表

> `game-designer` 提案一個具體玩法機制 → `student-tester` 挑一個學生身分實際試玩給回饋 →
> `game-designer` 看完回饋調整下一版 → 重複，直到收斂或判斷不值得再迭代。
>
> 為什麼要有這份表（不是直接叫兩個代理人互相呼叫）：`MAX_DEPTH=1` 不允許代理人互相呼叫，
> 這是機器層事實，不是設計選擇。跟 `mutator`↔`wp-manager` 用 `MUTATIONS.md` 的道理一樣——
> **非同步、透過同一張表留言**，由主線每輪居中轉發，讓「快速迭代」有一個具體、持久化的
> 落點，不必每輪都由主線口頭轉述「上一輪發生了什麼」。

## 為什麼要有這個機制（2026-09-14 楊老師提出）

「什麼樣的遊戲玩法對應什麼樣的學習內容、會產生什麼優缺點」這件事本身要收斂成知識
（見下方「跟 game-designer 自己 KB 的分工」），但知道抽象原則不夠——「怎麼樣在學習和
遊戲化誘因之間取得平衡」這種判斷，必須**讓模擬學生實際試玩**才拿得到具體回饋，不能
只靠 `game-designer` 紙上推演。`student-tester` 在 WP-9 那輪第一次被呼叫就抓到兩個
紙上審查完全沒發現的真實問題（安全網只接一站、降階按鈕原地鬼打牆）——這證明「實際走一次」
比「讀規格猜」更容易抓到真問題，遊戲化機制設計也該用同一招，而且要**常態化**，
不是等五棒循環走到「評估」棒才測一次。

## 跟 `game-designer` 自己 KB 的分工（不要混在一起）

- **`kb/game-designer.md`**：跨專案、跨時間都成立的**抽象知識**——「什麼類型的玩法（例如
  段位制、連續正確加成、稀有度收集）配什麼類型的學習內容（高頻詞背誦、文法規則內化、
  長篇閱讀）容易產生什麼優缺點」，這是可以帶到下一個專案用的原則性知識，**用 WebSearch
  查文獻＋本專案實測共同累積**，格式依 `kb/README.md` 分「有定論的研究」／「本專案的實測」／
  「我的判斷」三類。
- **這份 `PLAYTEST.md`**：**這個專案這一版具體機制**的迭代歷史——這次提的是哪個具體規則
  （例如「連續答對3題後，第4題答對給1.5倍XP」），哪個身分試玩後卡在哪、覺得無聊還是有動力，
  下一版怎麼改。這是「正在發生的設計對話」，不是抽象知識，兩者不要互相取代。

## 使用方式

1. **`game-designer` 提案時**：新增一列，機制要**具體到可以被試玩**——不是「加一個連續
   答對加成機制」，是「連續答對3題後，第4題起每題額外+2XP，斷掉歸零重算，UI 顯示一個
   小火焰圖示」這種程度。「對應學習內容」要講清楚這個機制**鼓勵的是什麼行為**（見
   `game-designer.md` 判準2「獎勵指向的行為」），不能只講機制不講對應到什麼學習目標。
   「預期優缺點」是 `game-designer` 自己先推演至少一種鑽法（`game-designer.md` 既有格式
   「學生會怎麼鑽」直接搬過來用）。
2. **`student-tester` 試玩時**：從五個情境（A-E，見 `student-tester.md`）挑一個跟這個機制
   最相關的身分（例如連續加成機制最該用 D「時間破碎」身分試——他最容易被打斷、最容易
   斷掉連續紀錄），實際依照機制描述逐步推演會發生什麼（不是重複 `game-designer` 已經講過的
   推演，要用試玩者的第一人稱視角走一次：看到什麼畫面、心裡怎麼想、在哪一步會想關掉）。
   回填「試玩身分＋逐步走查／卡點」欄，格式沿用 `student-tester.md` 既有的「我會在這裡
   放棄」風格。
3. **`game-designer` 看到試玩回饋後**：不是照單全收，是判斷回饋點出的問題要怎麼調整
   （或判斷這個回饋是揣測、不足以改設計，說明理由），填「調整方向」欄，決定要不要開下一列
   繼續迭代，還是判斷已經收斂、狀態改成「已收斂」。
4. **這是主線居中轉發的非同步迭代**，不是即時對話——每一輪呼叫誰、帶什麼上下文，由主線
   在派工時決定，通常是「讀 PLAYTEST.md 最新一列，接著往下做」這種指示。
5. **不確定值不值得繼續迭代時**：狀態填「擱置」並寫清楚為什麼（例如需要真人資料才能判斷、
   或已經超出這輪該處理的範圍），不要為了有東西寫而硬迭代下去。
