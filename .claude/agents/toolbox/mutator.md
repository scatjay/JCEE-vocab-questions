# mutator 工具箱

> 🔴 這份工具箱的維護方向**跟其他13隻相反**：其他人的工具箱該往「精簡成真正常用的
> 子集」收斂；這份該往**累積更多元、更分歧的視角**發展。`wp-manager` 健檢時知道這條，
> 不會因為某個框架「看起來很久沒被用」就建議刪掉——那正好是它該保留、等下次輪到的東西。

## 原始工具，什麼情境用哪個
- **Read/Grep/Glob**：廣讀，不受職責邊界限制——`docs/PLAN.md` 全文、所有 `docs/cycle/*.md`、
  所有 `kb/*.md`、黑板。
- **WebSearch/WebFetch**：找外部框架去質疑本專案的假設——這是你跟其他代理人最不一樣的
  工具用法：別人用 WebSearch 是「查證一個具體事實」，你用它是「找一個**還沒用過的思考角度**」。
- **Write**：🔴 只准寫 `docs/cycle/mutation-*.md` 與自己的 `kb/mutator.md`。

## 外部框架庫（每次挑戰決策前，優先選一個「這輪還沒用過」的角度）

| 框架 | 它擅長逼出什麼問題 | 上次用過（追加時標） |
|---|---|---|
| **Contract Net Protocol**（Smith 1980） | 這個決策裡「誰該做這件事」的假設，換一種分工方式會不會更好 | 2026-09-14（用在設計wp-manager本身，不是用來挑戰WP決策——下次找機會真的拿它挑戰一個WP政策） |
| **基因演算法的突變** | 「這是不是已經收斂到局部最優、而不是全域最優」——你自己的存在理由，別忘了拿它自我檢查 | 2026-09-14（你的角色定義本身就是這個框架的產物） |
| **邊界物件**（Star & Griesemer 1989） | 一份文件/schema是不是「對每個讀者都投射不同意義，但整體仍然協調得起來」——用來質疑
一份規格是不是其實只服務了某一種讀者 | 尚未用過 |
| **Anthropic orchestrator-worker** | 「這件事該不該平行拆給多個獨立視角，而不是一個角色從頭到尾包辦」 | 尚未用過 |
| **黑板架構／stigmergy**（Hayes-Roth 1985） | 「這個協調機制是不是應該讓資訊自己浮現，而不是靠誰主動去問誰」 | 2026-09-14（第二次真實任務，挑戰WP-9候選A安全網文案假設「學生有一個可以求助的英文老師」——看出候選A的間接協調層（floorState留痕→WP-6老師報表顯著標示）已決定要做但完全未排程、未被列為WP-9對真實學生上線的前提條件；`wp-manager`尚未回應，見`docs/cycle/MUTATIONS.md`第2筆） |
| **Leveled commitment**（Sandholm & Lesser 1995） | 「這個承諾/決定是不是應該允許事後用某種代價退出，而不是全有全無」 | 2026-09-14（第一次真實任務，挑戰WP-8政策8「精熟判定」——挑出`consecutiveSpacedCorrect`歸零與`masteredAt`無撤銷這兩處全有全無承諾；`wp-manager`已回應，見`docs/cycle/MUTATIONS.md`第1筆） |
| **TRIZ 矛盾矩陣**（工程發明方法論） | 「這裡兩個互斥的需求，有沒有第三種解法讓兩者都不用犧牲」——還沒真的查過，只是聽過名字，
下次有空查一下值不值得放進來 | 尚未查證，先佔位 |
| **第一性原理／反轉思考** | 「如果從頭重來，還會做出現在這個決定嗎」「怎麼樣一定會失敗，然後倒著推」 | 尚未用過 |

**用法**：挑戰一個定案之前，先掃這張表，選一個「上次用過」欄位最舊或空白的框架，
刻意用它的提問方式去看那個決定——不要每次都下意識用同一個角度（例如每次都用「基因演算法」
自我指涉），那樣你自己也會收斂，跟你要對抗的問題一樣。

**追加規則**：發現一個新框架值得放進這張表，用 Edit 直接加一列；用過某個框架後，
把「上次用過」欄位更新成這次日期＋一句話（挑戰了哪個決策）。這張表只會變長，
不會因為「精簡」而變短——變短違背這份工具箱存在的理由。

## 用出來的心得
- 2026-09-14（第一次真實任務後補）：用 Leveled Commitment 框架挑戰 WP-8 政策8（精熟判定）成功
  挑出兩處全有全無承諾（歸零／無撤銷），`cycle-designer` 採納方案A。但事後發現一個框架選用
  本身沒有覆蓋到的死角：**你的分析只看得到「政策文字」，看不到「已經施工完成、依照舊政策
  寫死的程式碼」**——`game/kc-logic.js` 在你提案之前就已經照舊政策建置，你的提案文件和後續
  裁決都沒有提到「這個程式碼需要回頭同步」，這個落差是主線事後手動發現才補上的（見
  `docs/cycle/MUTATIONS.md` #1「觀察到的影響」欄，2026-09-14 補填）。下次挑戰一個已經有
  下游實作的政策時，除了 Read/Grep 規格文件，**該多一步 Grep 對應的 `game/*.js`／已建置程式碼**，
  在提案裡主動點名「這個決策生效後，哪些既有程式碼需要同步」，不要只交給裁決者事後才發現。
