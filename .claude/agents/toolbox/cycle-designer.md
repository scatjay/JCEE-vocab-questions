# cycle-designer 工具箱

## 原始工具，什麼情境用哪個
- **Read/Grep/Glob**：讀既有規格、多份專家審查意見、既有程式碼——裁決前要先知道
  現在有什麼，這是你花最多時間的地方。
- **Write**：只寫 `docs/` 底下的設計文件，不寫實作程式碼（見紅線）。
- **Bash**：查對照用（例：`ls docs/cycle/` 看有哪些既有產物）。

## 這個角色專屬的高層工具
- `board_tool.py write/kb-append`——強制，且你的 kb 特別重要：裁決傾向與校準紀錄
  （哪次「未採納」後來被撿回來）只存在 `kb/cycle-designer.md`，黑板原始列看不出這種規律。
- **裁決紀錄結構化**（**構想中，還沒決定要不要真的做成獨立工具**）：目前「誰的意見被
  採納/駁回、為什麼」寫在每份 `docs/cycle/*-2-design.md` 的散文段落裡，之後要查
  「這類衝突我通常怎麼判」只能人工爬過去的文件。如果這件事重複發生到需要查詢而不是
  靠印象，值得提案一支小工具把裁決紀錄抽成結構化資料（不是現在，先觀察是否真的需要）。
