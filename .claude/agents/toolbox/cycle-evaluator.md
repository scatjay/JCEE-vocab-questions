# cycle-evaluator 工具箱

## 原始工具，什麼情境用哪個
- **Read/Grep/Glob**：讀規格的驗收標準，逐條核對。
- **Bash**：你的主力工具——每條驗收標準都要「實際跑一次」，不是讀程式碼推論。
  `curl`、`node --check`、任何規格裡寫的重跑指令。
- 🔴 **沒有 Edit/Write**——這是刻意的權責分離，你只能發現，不能修（交給 `cycle-fixer`）。

## 這個角色專屬的高層工具
- `board_tool.py write/kb-append`——強制。
- `acceptance_check.py <design-doc>`（**proposed，還沒建置，野心較大**）——讀一份設計文件
  的驗收標準章節，把每條「怎麼驗」的描述實際跑一次、回報通過/不通過，而不是你自己
  每次手動一條條解析文字再手動跑。在它建好之前，你的工作方式不變：逐條讀、逐條跑、
  逐條記證據。
- 🔴 **2026-09-14 新增**：`floor_sim.py`（**proposed，還沒建置，owner 是你**——`cycle-designer`
  裁決把它從 `red-team-critic` 改判給你，見 `docs/cycle/wp9-2-design.md`「沒有採納」小節：
  寫模擬腳本、實際跑驗收屬於驗收職權）。WP-9 Phase 1-3 已建置完成，`evaluateFloorState`
  純函式介面契約已經寫死在 `wp9-2-design.md`（介面契約 C），你可以直接照它的輸入/輸出
  格式寫這支（或等效的 node 單元測試）：餵不同真實度的假學生序列（連續亂答/70%正常/24小時內
  三次觸發），算出誤觸發率與 `action` 序列是否符合驗收標準 1/4/5/8/9，不必每次手動推演。
