# 智能學習系統 · 設計代理人團隊

一組從**構思 → 設計 → 開發 → 評估 → 修正**完整循環的代理人，
專門用於設計「智能學習系統」，以本 repo（JCEE 英文題庫遊戲化）為第一個驗證案例。

**動工前每一棒都要先讀 [`_DOMAIN.md`](_DOMAIN.md)**（領域簡報，含北極星目標）。

---

## 團隊組成

### 五位領域專家（帶專業視角，在設計與評估階段各自發言）

| 代理人 | 他問的問題 | 他負責擋住什麼 |
|---|---|---|
| [`english-teacher`](english-teacher.md) 英文老師 | 這句英文說法對不對？學生真正卡在哪？ | **內容錯誤**（比沒內容更糟，學生會把錯的記起來）；AI 家教自行編造英文解釋 |
| [`learning-scientist`](learning-scientist.md) 學習專家 | 這真的會產生學習嗎？ | 做出計分板而不是學習系統 |
| [`assessment-expert`](assessment-expert.md) 學習評測專家 | 這個數字憑什麼代表學習？ | 把使用量包裝成學習成效 |
| [`game-designer`](game-designer.md) 遊戲設計師 | 他明天會回來嗎？獎勵在鼓勵什麼？ | 獎勵量而不是獎勵有效行為 |
| [`ux-designer`](ux-designer.md) 介面與互動體驗 | 累了一天的高中生用手機做得到嗎？ | 3 分鐘模式花 40 秒在設定 |

### 紅隊與測試員（站在會被辜負的人那一邊）

| 代理人 | 立場 |
|---|---|
| [`red-team-critic`](red-team-critic.md) 紅隊 | 這個系統對誰沒用、對誰有害、什麼條件下失效。**常設挑戰第一條：M 型化底下連基本閱讀都吃力的學生。** |
| [`student-tester`](student-tester.md) 學生測試員 | 用五種學習情境的學生身分實際走流程。呼叫時指定跑哪一個：<br>**A** 高一・基礎尚可・時間穩定（北極星使用者）<br>**B** 高三・落後・焦慮<br>**C** 低閱讀能力（M 型化）<br>**D** 時間破碎（打工／照顧家人）<br>**E** 能力好但沒動機 |

> 🔴 **`student-tester` 是模擬的，不是真的學生。** 它抓得到明顯的牆，抓不到真實學生才有的反應
> （什麼讓他覺得丟臉、他到底會不會回來）。它是**真人測試前的便宜前篩，不是替代品**——
> 每次產出都會列出「這個情境最需要真人測試的問題」，那份清單才是找真學生來測時的題目。

### 三個流程角色

| 棒次 | 代理人 | 職責 |
|---|---|---|
| 1 構思 | [`cycle-ideator`](cycle-ideator.md) | 框定問題、提出真正互斥的選項與代價 |
| 2 設計／整合 | [`cycle-designer`](cycle-designer.md) | **裁決專家之間的衝突**，產出帶可驗證驗收標準的規格 |
| 3 開發 | [`cycle-builder`](cycle-builder.md) | 只做規格範圍內的事，自驗後逐檔 commit |
| 4 評估 | [`cycle-evaluator`](cycle-evaluator.md) | 實跑驗收標準。**刻意沒有 Edit/Write——只能發現不能修** |
| 5 修正 | [`cycle-fixer`](cycle-fixer.md) | 只修被點名的，修完重驗，誠實回報沒修的 |

## 循環怎麼跑（主線負責調度，代理人之間不互相 spawn）

```
   ┌─ 1 構思 ──────────────────────────────────┐
   │   cycle-ideator → 選項與推薦               │
   │            ↓ 人決定方向                    │
   ├─ 2 設計 ──────────────────────────────────┤
   │   五位專家 ＋ red-team-critic 各自發言      │  ← 可平行
   │            ↓                               │
   │   cycle-designer 裁決衝突 → 規格＋驗收標準  │
   │            ↓ 人確認                        │
   ├─ 3 開發 ──────────────────────────────────┤
   │   cycle-builder → 實作＋自驗＋commit        │
   │            ↓                               │
   ├─ 4 評估 ──────────────────────────────────┤
   │   cycle-evaluator（功能面，實跑驗收標準）    │  ← 可平行
   │   五位專家＋紅隊（領域面）                   │
   │   student-tester ×5 情境（走查，找牆）       │
   │            ↓                               │
   │   ⚠ 真人學生測試（模擬測試員的清單＝題目）    │  ← 不可省略
   ├─ 5 修正 ──────────────────────────────────┤
   │   cycle-fixer → 修＋重驗                   │
   │            ↓                               │
   └─→ 沒修完的／要改設計的 → 回第 2 棒 ─────────┘
```

**調度原則**
- 代理人**不互相 spawn**（全機紅線：手動 spawn ≤3–5、每日上限 60）。主線讀各自的回報後決定下一步。
- 第 2 棒與第 4 棒的專家意見**可以平行**（他們互不依賴）。
- **評估與修正必須是不同角色**：寫的人會不自覺用「我知道它應該可以」代替「我驗過它可以」。

## 產物放哪

- 各階段的輸出：`docs/cycle/<主題>-<棒次>-<階段>.md`
  （例：`pomodoro-1-options.md`、`pomodoro-2-design.md`、`pomodoro-4-eval.md`）
- 各代理人的知識庫：[`kb/<agent>.md`](kb/README.md)，**用一次長一次**，不是一次性研究。
