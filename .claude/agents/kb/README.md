# 代理人知識庫（kb/）

每個帶領域專業的代理人維護**一份自己的**知識庫：`kb/<agent-name>.md`。

## 規則

1. **動工前先讀自己的 KB**，站在上次的結論上，不要每次從零開始。
2. **跑完後追加**：這次學到什麼、哪個判準被真實情況推翻、哪個假設被證實。
   追加時標日期與來源，**不要覆寫舊結論**——被推翻的往下移並標明「已被 YYYY-MM-DD 推翻」。
3. **區分三種內容**（混在一起的 KB 會害下一輪做錯決定）：
   - `有定論的研究`：附出處，且要是你真的讀過的，不是憑印象
   - `本專案的實測`：我們自己量到的數字
   - `我的判斷`：沒有證據支撐、但目前這樣假設
4. 🔴 **不准猜出處**。引用研究要能指出具體來源；查不到全文就標「僅摘要」或「未讀」。
   （這是全機規則：文獻逐篇標讀取程度，抓不到全文的不要靜默跳過。）

## 首次執行：各代理人該先補的理論

🔴 **這是一個獨立的第一輪任務，不要跟具體審查任務塞在同一輪**（2026-09-14 楊老師
明確糾正）：領域專家第一次被呼叫時，若KB是空的，**第一個任務就該是「建立知識庫」
本身**——把下表列的理論方向找**有實證、可操作、優先讀全文**的權威來源深讀後寫進KB，
不要在同一輪裡又塞一個具體的WP/機制審查（例如「順便審查一下WP-8」）。理由：
任務時間壓力會把「認真建立知識庫」拖成「臨時查兩篇應付這次審查」，讀取程度
永遠停在「僅摘要」，這正是要避免的「上網亂爬」模式——`game-designer` 深讀
《Patterns in Game Design》8個具體pattern之後、判斷品質才真正提升，就是這個
順序做對的示範。只有KB已經有一定厚度後，才適合排具體審查任務。

以下是建議的起點，不是清單義務。研究時優先找**有實證、可操作**的，
不要收集一堆名詞卻沒有可據以設計的結論。

🔴 **例外：`ux-designer` 的「先建KB」不是讀理論文獻**（2026-09-14 楊老師補充）。
`learning-scientist`／`assessment-expert`／`game-designer` 這類角色的核心知識是
**抽象理論**，天生適合靠深讀學術文獻／專書建立；但 `ux-designer` 的可用性判斷
（進入摩擦、資訊層級、認知負荷卡在哪）很大一部分只有**實際操作過介面**才感受得到——
這種透過系統性走過畫面、記錄具體卡點累積出的實用判斷，是一種「偽具身性」知識，
比讀UX理論摘要更貼近這個角色真正倚賴的知識類型。⇒ `ux-designer` 的「第一輪建KB
任務」該是「找幾個本專案（或可比對的同類產品）的具體畫面，實際走一次操作流程，
記錄具體卡點」，核心分類是三分類裡的「**本專案的實測**」，不是「有定論的研究」；
通用UX理論（Fitts's Law、認知負荷理論）只是輔助校準，不是它知識庫的主體。

## 流程角色與管理師的 KB：累積的是「這條線自己的歷史」，不是理論

以下角色沒有外部理論要補（它們的判準來自流程設計本身），KB 累積的是**這條線跑過的實例**。
**不是抄黑板**（`_runlog.jsonl` 是「發生了什麼」的共用帳本，誰都能讀）——KB 是**經過篩選、
有判斷力的結論**，而且每個角色該累積的東西性質不一樣，不是同一句「記住哪裡錯過」套七次：

| 代理人 | KB 該累積什麼（具體到「這是什麼形狀的知識」） |
|---|---|
| `cycle-ideator` | **本專案特有的硬約束清單**（例：純 vanilla 無建置流程、不能引入 React/Tailwind），一旦在某個 WP 因此排除過某個選項，下次遇到類似情境直接套用、不用重新推導一次「這樣不行」；以及「假多元」的具體案例——哪次提的3個選項事後被發現其實是同一招換皮 |
| `cycle-designer` | **自己的裁決傾向與校準紀錄**——例如「學習專家 vs 遊戲設計師衝突時我傾向站哪邊、為什麼」，附上後來被證實對或錯的案例；「未採納」的意見清單與各自的重新觸發條件（WP-8 裁決文件裡已經示範了這個格式，直接沿用） |
| `cycle-builder` | **這個 repo 的地雷清單**——例：各站答題引擎命名不統一（§4 表）、RTDB 規則必須合併不能覆蓋、`cards/` 已有 SRS 不要重做；每記一條就是下次少踩一次 |
| `cycle-evaluator` | **這個團隊的「說做完但沒有」慣性模式**——不是通用QA常識，是「這個 builder / 這種任務類型，最常在哪裡自稱驗證過但其實只是推論」的具體校準 |
| `cycle-fixer` | **根因分類帳**——修過的問題裡，追蹤到同一個 schema 缺口/同一個設計假設錯誤的次數；累積到某個閾值就該是「這其實是系統性問題，該回頭改設計」的證據，不是繼續逐一修 |
| `student-tester` | **五個情境（A-E）各自模擬出的牆，逐條標「已被真人測試證實」／「已被推翻」／「尚未驗證」**——這是全隊最該長的一份 KB，因為它的存在理由就是「真人測試前的便宜前篩」，準確率能不能隨時間提升，直接看這份累積得好不好 |
| `wp-manager` | **團隊動態的元資料**——哪隻代理人的建議常被主線採納/不採納、自己過去「建議下一步」的命中率、哪個 WP 的狀態標記跟實際落差最大及為什麼（例：草稿先於循環存在、審查有模擬版混在真身裡）；**加上工具生態的判斷**——哪支工具的 friction 累積到該回頭改、哪支長期沒人用。這是管理師的判斷力本身，黑板原始事件列裡看不出這些規律 |
| `mutator` | 過去提案的下場——哪些被採納、哪些被否決、哪些沒人理；分辨「值得認真提的突變」跟「為挑釁而挑釁」的判斷力，就是從這裡累積出來的，沒有這份紀錄它會變成為反對而反對 |

## 輪休模式（Sabbatical）：對抗知識庫的單向累積

`kb/` 的規則是「只增不改、被推翻的往下移不刪除」——這解決了「亂改歷史」的問題，
但引入了另一個風險：**KB 只會單調變厚，不代表代理人真的在重新檢視舊結論**。
一份跑了很多輪、卻從來沒有任何一條「已被 YYYY-MM-DD 推翻」紀錄的 KB，
兩種可能都存在，但後者更常見也更危險：要嘛是舊結論全部禁得起考驗（少見），
要嘛是這隻代理人只在往上疊加新觀察，從來沒有主動回頭質疑過去的判斷——
這跟大學教授如果永遠不休假、永遠留在同一個計畫裡，會漸漸只看得見自己既有框架能解釋的東西，
是同一種停滯。

**休假不是純休息，是被送去做別的事、帶新東西回來**，具體做法：

1. **觸發訊號**（`wp-manager` 團隊健檢時檢查）：一隻領域專家（`english-teacher`／
   `learning-scientist`／`assessment-expert`／`game-designer`／`ux-designer`／`red-team-critic`）
   的 KB 累積 ≥3 次「本專案的實測」或「我的判斷」條目，卻**一次「已被推翻」都沒有**——
   標記為休假候選，寫進 `wp-manager` 的回報「建議：該排一輪 XXX 的休假」。
2. **休假輪怎麼跑**：呼叫該代理人時，**任務不是審查某個具體 WP 產物**，而是：
   - 重讀自己完整的 KB（含已推翻的舊條目），逐條問「這個結論現在還站得住嗎」——
     找不到理由推翻就明講「重新檢視過，仍然成立」，不是義務性地一定要推翻什麼
   - 花這一輪去補 `kb/README.md`「首次執行：各代理人該先補的理論」表列的那些理論
     （或找這個理論領域最近有沒有新進展），這部分**不綁定 JCEE 的具體任務**，
     就是刻意的、對外的知識更新
   - 回來後在 KB 裡寫一段「休假回顧」：這次重新檢視有沒有推翻什麼、外部補的理論
     有沒有讓既有判準需要調整
3. **不是排程，是訊號驅動**：這些代理人是被呼叫時才存在的子代理，沒有行事曆概念，
   所以休假不是「每隔幾週」，是**上面那個訊號出現時，下一次呼叫該隻代理人就排成休假輪**，
   而不是繼續累積第 4 次、第 5 次同方向的觀察。

## 共用知識庫（跨代理人，不屬於單一角色）——`kb/_SHARED_*.md`

上面的規則是「每個代理人一份自己的KB」，但有些知識本身**不屬於單一角色的判斷力**，
是這條線持續累積的**共用領域知識**，值得獨立維護、被多個角色引用——這類檔案用
`_SHARED_` 前綴跟一般 `kb/<name>.md` 區分，格式規則相同（區分研究/實測/判斷、
標讀取程度、被推翻的往下移不刪除）。

目前有：
- `_SHARED_language_learning_gamification.md`（2026-09-14 楊老師提出建立）——語言學習
  遊戲化的現有做法（業界產品/學術文獻），主要由 `game-designer` 維護寫入，但
  `learning-scientist`／`ux-designer`／`student-tester`／`english-teacher` 動工前都該讀，
  發現新材料任何角色都可以追加。

判斷一份知識該不該獨立成 `_SHARED_*.md`（而不是塞進單一代理人KB的一節）的原則：
**這份知識是不是有超過一個角色會反覆需要引用它**——如果只有一個角色用得到，就留在
它自己的KB裡就好，不要為了「看起來系統化」而過度拆檔案。

## 對本專案最重要的一條

北極星是**每天 15–30 分鐘、從高一開始、900 天**（見 `.claude/agents/_DOMAIN.md` §0）。
多數遊戲化與學習設計的文獻談的是幾週的實驗；**找證據時要特別留意「這個效果撐得過幾個月嗎」**，
撐不過的機制不要當成主要支柱。
